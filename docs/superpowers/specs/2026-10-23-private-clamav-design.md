# Private version-bound ClamAV and customer review

Owner request authorizes local implementation/testing and costed deployment preparation, not AWS changes. Preserve GuardDuty compatibility without enabling it. No public antivirus or daemon endpoint.

Recommended path: existing private versioned uploads -> prefix-filtered S3 event -> encrypted SQS with DLQ -> private outbound-only ClamAV container -> separate private worker-write/API-read result bucket. Each result binds bucket, key, exact VersionId and deterministic attempt ID, engine/signature version, definition build time, scan time, verdict and a curated reason. The upload API never accepts result authority. Existing finalization/review/download gates resolve the configured scanner. Result writes are conditional and immutable: duplicate/out-of-order processing cannot overwrite a terminal result or approve another version. Transient failure emits no clean result, retains queue receipt and retries up to redrive limit. Terminal non-clean results require corrected reupload to a new object version; no force-clean operation.

Alternative: Lambda container with 4 GB memory and 1 GB temporary storage, SQS source and reserved concurrency. This can reduce idle cost but requires a separate handler, signature distribution/cold-start benchmark and lifecycle design. Not interchangeable with the long-running poller. A VM lowers base compute costs but adds OS patching/recovery ownership. Fargate is proposed for the first deployed scanner; no alternative is enabled automatically.

Customer requirements are configuration plus versioned consent: no mandatory default document list. New customer application/document records and audit events are independent from provider/vehicle records. Scan-clean only permits manual review; all required documents must be accepted. Publication checks status, current policy, document decisions and clean exact-version evidence. Suspension/rejection/resubmission preserve historical rows. The owner previously said Aadhaar/PAN; the newest request asks to identify unconfirmed requirements, so legal/privacy/document policy confirmation remains a release gate.

Local verification uses real ClamAV against synthetic clean/EICAR/encrypted/unsupported files with no network during scanning. Storage/SQS adapters are simulated in local worker tests; PostgreSQL application state is real and isolated. Existing fixtures may opt into APP_ENV=test-only customer eligibility simulation; separate customer tests disable it and exercise real review gates. Production cannot activate simulation.

Resource envelope: 10 MB files, 40 MB expanded scan data, 100 embedded files, recursion 8, PDF page limit 200, image pixel limit 25 million, parser+engine subprocess wall clock 180 seconds. Definitions older than 48 hours fail closed; refresh every 12 hours. Initial 60-second engine startup failed under local Docker CPU/memory pressure; 120-second engine / 180-second overall bounds are being validated. Fargate proposal uses 2 vCPU/4 GB memory; official ClamAV guidance recommends 3-4 GiB. All temporary files live in a context-managed directory; processing emits only curated status logs.

AWS inspection currently blocked: no exposed S3/IAM connector tool and default credential chain has no credentials. Do not infer account, bucket configuration, CORS, policies, notifications or service/free-tier eligibility from historical reports. Inspect and merge actual existing bucket configuration only after personal account access is verified. Never use employer resources.
