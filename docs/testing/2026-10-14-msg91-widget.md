# MSG91 phone verification — configuration and verification

## Implemented boundary

Sign in using existing email/password → Account help → Trip contact → save mobile with current password → Verify saved phone (send OTP). Scripts load only after explicit action, first `verify.msg91.com`, then `verify.phone91.com`. React ignores stale/cancelled callbacks and removes its widget on unmount. A widget callback is not authentication evidence.

The frontend posts the opaque proof to `POST /api/v1/auth/mobile/verify-widget`. The API requires an active authenticated account and validates the proof through `POST https://api.msg91.com/api/v5/widget/verifyAccessToken`, using the private account Authkey in its header. Only a success response containing a valid phone matching the locked account can set `mobile_verified`. The consumed proof is hashed and recorded; repeated use conflicts. No TransivoX login token or new role is returned. This is phone ownership verification, **not passwordless sign-in or KYC**.

Provider contract: [MSG91 server verification](https://docs.msg91.com/otp-widget/verify-access-token) and [widget integration](https://msg91.com/help/sendotp/how-to-integrate-the-new-login-with-otp-widget). The documented server success message contains the verified identifier. Missing/malformed/email identifiers fail closed. Server configuration/timeout errors do not grant verification. No proof, OTP, account Authkey or raw provider response is logged or returned. Input validation errors omit submitted input values.

## Environment variables

| Variable | Local placement | Vercel project | Value |
|---|---|---|---|
| `VITE_API_URL` | root `.env.local` | frontend (`trucksetu-whri`) | Approved API URL ending `/api/v1` |
| `VITE_MSG91_WIDGET_ID` | root `.env.local` | frontend | Widget ID from your supplied snippet: `366a6d6a6b6a333638313134` |
| `VITE_MSG91_WIDGET_TOKEN_AUTH` | root `.env.local` | frontend | The **widget-only** tokenAuth supplied by you. Do not substitute account Authkey. Not hardcoded in source |
| `MSG91_WIDGET_ENABLED` | backend environment / backend `.env` | API (`trucksetu-api`) | `true` only when deliberately configuring this integration; default `false` |
| `MSG91_AUTH_KEY` | backend environment / backend `.env` | API only | Private **account Authkey**, obtained from MSG91 server-side integration settings. This is different from widget tokenAuth |

All `VITE_*` values are public in the browser. Never create `VITE_MSG91_AUTH_KEY`. Keep local environment files ignored and do not paste secrets into chat. Restrict widget tokens/origins in MSG91 where supported; configure your owned domain and approved localhost/staging origins. Never reuse production credentials in ordinary automated tests.

Trip pickup/delivery OTP is a separate template flow: it still needs backend `MSG91_TEMPLATE_ID` and `MSG91_OTP_VARIABLE` (default `OTP`) plus the account Authkey. Adding a widget does not configure the trip template or prove real SMS delivery.

Restart local API/Vite after changing configuration. Vite substitutes public variables at build time. Vercel variables must be applied to the correct frontend/API projects and selected environments; do not deploy this build until the release/migration gates pass and deployment is separately authorized. Setting a variable is not proof of delivery.

## CSP and SDK checks

For a custom CSP, permit the two exact widget script origins and MSG91's documented widget API origin in `connect-src`. The container nginx example includes bounded MSG91 origins; use the exact deployed TransivoX API origin rather than its localhost example. If your widget enables CAPTCHA, additionally allow the required CAPTCHA script/frame/connect origins according to its provider documentation; do not disable CSP or allow every origin. The widget SDK's own overlay is above the account dialog. Live SDK/CAPTCHA/domain/balance behavior was not executed in implementation.

## Remaining gates

- The owner approved exclusivity only after verification. Signup/contact inputs are canonicalized; unverified claims do not block verification, but another verified owner (including a suspended owner) does. Saving the same canonical phone preserves verification; changing it clears verification. Migration `20261014_22` enforces verified-only uniqueness and canonical verified values, refusing invalid/conflicting verified legacy claims rather than selecting an owner. Real PostgreSQL migration and concurrent-ownership tests still require the isolated database; offline compilation alone is not execution evidence.
- A real MSG91 verification round trip, SMS delivery, allowed-domain/token settings, CAPTCHA and billing remain unverified. Perform an explicitly approved staging test with your own number only after local DB gates pass. Clicking the configured widget can send a billable SMS; no such action was performed here.
- No phone-only login, mandatory-phone gating of existing password sign-in, mobile-based account recovery or role elevation was added.
